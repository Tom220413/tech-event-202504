# 開発ガイドライン

## 開発方針

### テスト駆動開発（TDD）
- **Red-Green-Refactor**サイクルを徹底
- 新機能追加時は必ずテストから作成
- バグ修正時は再現テストを先に作成
- カバレッジ80%以上を維持

### コード品質
- ESLintルールを厳格に適用
- 関数・コンポーネントは単一責任原則
- 型安全性を重視（JSDocコメント必須）
- エラーハンドリングを徹底

### アーキテクチャ
- 関心の分離を徹底
- ビジネスロジックとUIロジックの分離
- 再利用可能なコンポーネント設計
- API層とデータ層の明確な分離

## Claude Code活用ルール

### 基本原則
1. **テストファースト**: 新機能は必ずテストから作成
2. **段階的実装**: 小さな単位で実装・テスト
3. **明確な指示**: 具体的な要件と期待結果を明記
4. **レビュー必須**: 生成されたコードは必ずレビュー

### 指示のテンプレート
```
## タスク概要
[何を実装するか]

## 要件
- [具体的な要件1]
- [具体的な要件2]

## テスト要件
- [テストケース1]
- [テストケース2]

## 技術的制約
- [使用する技術・ライブラリ]
- [既存コードとの整合性]

## 期待結果
[どのような動作を期待するか]
```

### 禁止事項
- テストなしでの機能実装
- 既存テストを壊す変更
- ドキュメントなしの新機能
- セキュリティ考慮なしの実装

## ファイル命名規則

### テストファイル
- ユニットテスト: `*.test.js`
- 統合テスト: `*.integration.test.js`
- E2Eテスト: `*.e2e.test.js`

### コンポーネント
- Reactコンポーネント: `PascalCase.js`
- ユーティリティ: `camelCase.js`
- 定数: `UPPER_SNAKE_CASE.js`

## コミットメッセージ規約

```
type(scope): description

feat: 新機能
fix: バグ修正
test: テスト追加・修正
refactor: リファクタリング
docs: ドキュメント更新
style: コードスタイル修正
```

## レビューチェックリスト

- [ ] テストが追加されているか
- [ ] 既存テストが通るか
- [ ] ESLintエラーがないか
- [ ] セキュリティ問題がないか
- [ ] パフォーマンス問題がないか
- [ ] アクセシビリティが考慮されているか
- [ ] ドキュメントが更新されているか
